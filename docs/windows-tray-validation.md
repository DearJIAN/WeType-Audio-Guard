# Windows 托盘与 EXE：验证结果、修复经过及安全边界

> 本文记录从 CLI 原型至 **WeType Audio Guard 1.1** 的实际测试和局限。2026-11-02 的 CLI 记录另见 [原始实测](field-test-2026-11-02.md)。早期规划文档保存在 `docs/superpowers` 作为历史档案，并非当前运行说明。

## 当前状态（2026-11-03）

- **正式功能**：打开程序后自动请求开启保护；启用状态的菜单带对勾；允许暂停/恢复；提供本地「查看日志」（记事本）及「复制日志」（剪贴板）。
- **持续运行**：音频工作子进程持续扫描，不设置总运行时长；每一次新的微信录音有**独立的 2 秒恢复窗口**，每个会话最多尝试恢复一次。
- **错误处理**：CLI 冲突检测移至启用阶段；音频快照读取异常时保守中止恢复并重建基线；子进程无响应阈值 12 秒，仍支持受限清理。
- **安全**：不采集语音、会议内容或主动上传日志。不更改麦克风静音，也不修改系统通信配置或开机自启。
- **环境**：Windows 10/11 x64；GitHub Actions 使用标准 CPython 3.12 与固定构建依赖。

## 实际发现与修复经过

### 1. CLI 在真实 Windows 环境通过

2026-11-02 原始命令行 `--diagnose` 已识别微信语音录入时的多应用静音，
`--protect` 在用户电脑上确实解除 `ldremote.exe` 与 `wemeetapp.exe`
的会话静音。原 `wetype_audio_guard.py` 和 `GuardPolicy` 保持不变。

### 2. 早期托盘 EXE 报音频工作进程超时

旧 v1.0.1 EXE 在 12:32 的录音中已记录 `Playback mute restored`，
但随后因 3 秒工作进程心跳阈值报 `worker-stopped`。
将心跳容忍阈值调整为 12 秒后，不再出现该类误判，仍保留真正卡死时的终止清理。

### 3. 旧托盘声音恢复太迟

第二轮实测在恢复每个播放会话前记录：
- `Slow CLI conflict inspection: 2.08s`
- `Slow CLI conflict inspection: 2.06s`

逐个候选应用重复遍历全系统进程，给同轮多应用恢复额外增加约 4 秒以上耗时。
1.1 将 CLI 冲突检查移到用户启用保护的监督阶段，录音中的恢复路径不再执行该慢检查。
由于原 CLI 无法使用托盘单实例互斥锁，**仍不得同时运行 CLI --protect 和托盘**。

### 4. 修复后 Windows 真实声音验收

2026-11-03 用户电脑上进行了三轮独立微信语音录入：

| 录音开始 | 恢复次数 | 记录的检测后延迟 | 下一轮音频静音回读 |
| --- | ---: | --- | --- |
| 13:02:45 | 2 | 0.02 秒 × 2 | unmuted=2 muted=0 missing=0 recording=ON |
| 13:02:55 | 2 | 0.02 秒 × 2 | unmuted=2 muted=0 missing=0 recording=ON |
| 13:02:59 | 2 | 0.00 秒 × 2 | unmuted=2 muted=0 missing=0 recording=ON |

总计 **6 次成功解除静音调用、3 次回读均解除静音**。
用户确认录音期间其他应用声音正常，最新托盘日志无新增错误。

以上 `delay_since_detect` 是发现当前录音状态到完成恢复调用的时间，
**不是从用户实际按下语音输入键到恢复的端到端延迟**。
实验不等于证明任何软件、音频设备或长期使用场景均正常。

用户还确认后续自动开启、状态勾选、查看/复制日志版本的实际体验测试通过。

## Windows 自动化验收

1. 运行 Python 编译检查和原 CLI `--self-test`。
2. 运行 **46 项单元测试**：包含基线、候选判断、故障、暂停竞态、慢扫描、工作进程监管、多应用快速恢复、回读、状态菜单、自动开启、日志查看和复制。
3. 使用 GitHub Actions Windows runner 构建 PyInstaller 单文件 EXE。
4. 执行 `--package-smoke-test`（冻结导入与图标）和
   `--frozen-tray-smoke-test`（真实托盘 UI 消息、模拟音频子进程启动与退出）。
5. 自动核对 EXE SHA-256 并制作包含必要许可证的 ZIP。

**自动测试不依赖真实音频硬件**；现场的音频恢复由上面真实 Windows 记录支撑。
本机 Conda 或其他 Python 环境打包仍可能出现缺少 `_ctypes` DLL 的错误，
建议使用 GitHub Actions 的发布产物，或用独立的标准 CPython 构建环境。

## 用户复验

请先退出其他版本的鲸鱼托盘和 `python wetype_audio_guard.py --protect`。
启动正式 EXE，程序会自动请求启用保护；等待没有录音时建立稳定基线，
再播放普通视频并启动微信输入法语音识别。右键检查状态和恢复次数。
用户可手动暂停、重新启用或退出。

单实例互斥只适用于托盘程序自身；对于独立 CLI，启用时执行保守冲突检查，
无法承诺二者有强双向互斥。故障、设备变更和静音历史未知时采取保守策略。

日志路径为 `%LOCALAPPDATA%\WeTypeAudioGuard\logs`。
菜单「查看日志」打开近期合并日志；「复制日志」将近期合并日志复制到剪贴板，
可自行粘贴并分享，**程序不会自动上传**。

## 未完成或不能保证的事项

- 微信输入法可能在同一轮录音再次静音；当前每轮每会话仅解除一次。
- 在录音前建立基线是必要条件；录音中才启用的场景需等待下一次稳定空闲基线。
- 当前恢复窗口可能误解除用户在该时间段主动设置的静音。
- 未普遍验证所有音频设备、驱动、显示缩放比例、热插拔、全天长期运行。
- 暂无代码签名、开机自启、自动更新和 Windows 安装器。
- `docs/superpowers` 目录保留早期已完成的设计与实现记录，仅供历史参考。
