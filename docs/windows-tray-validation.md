# Windows 托盘阶段二验证与本机验收

## 当前状态

开发分支：`feat/windows-tray`。CLI 基线为 `main` 的 `3048560`，保持源码字节与保护算法不变。原 CLI 已有的 2026-11-02 Windows 成功实测仍有效；本托盘尚未完成用户真实播放恢复验收，不应合并到 main。

## 设计的最小调整

为满足退出无残留和设备异常不阻塞托盘，将音频工作线程放入一个 `spawn` 子进程。该进程主线程是唯一的 COM 所属线程；UI 进程仅用一个监督线程收发状态。正常启停复用该进程；原生调用无响应时有界终止自己创建的进程。不会终止用户其他 Python、CLI 或会议进程。

暂停是异步请求，只有确认后才显示“已暂停”；已进入 Windows 的操作无法撤回。状态传递不包含 COM 引用，图标更新通过 Windows 消息回到 UI 线程，菜单只在打开/点击时更新，避免后台线程销毁正在显示的菜单。

原 CLI 文件不变，不能强制其使用新的锁，因此采用托盘单实例强互斥、CLI 保护进程保守检测和明确警告。命令行检测与写入之间仍有竞态，不承诺双方强互斥。检测基于标准 Python/Pythonw 运行脚本；重命名解释器、自定义启动器或脚本副本可能无法识别，用户不得并行运行两个保护程序。

## 用户 Windows 验收步骤

请在非正式会议环境进行。启用保护会主动解除符合条件的播放静音；它不操作麦克风、Windows 通信设置或全局音量数值。外放可能带来回声。

1. 停止已有 CLI `--protect`，保留正常的播放程序；不要同时开启另一个保护工具。
2. 安装 `requirements-tray.txt` 后执行 `python .\wetype_audio_tray.py`。确认灰鲸、已暂停、恢复次数为 0；语音输入时暂停状态不恢复声音。
3. 再启动一次托盘，确认第二个实例退出；第一个实例继续工作。
4. 在没有语音输入时点击“启用保护”，等待稳定基线后开始播放和微信输入法语音识别。确认蓝鲸与录音状态，符合条件时恢复计数增加，实际声音恢复。
5. 录音前手动静音一个无关播放会话，确认工具不会解除它。录音期间新建的静音会话也不应被恢复。
6. 暂停后，在微信输入法已经录音时启用，确认本轮不会立刻恢复；结束录音并等待稳定空闲基线，再次录音才恢复。
7. 多次启用/暂停，确认只有一个本托盘 UI 进程及一个音频子进程；暂停确认后不再恢复。进程名称都可能显示为 Python，请用任务管理器的命令行及父子关系区分，勿误结束其他程序。
8. 在可中断的场景插拔音频设备；确认错误可见且不无条件解除静音，恢复连接后必须重新建立基线。超过 watchdog 阈值会要求退出后重启。
9. 打开菜单检查计数与状态；检查 Windows 100%、150%、200% 缩放下鲸鱼辨识度。图标可能在系统托盘折叠区。
10. 通过“退出”关闭，确认图标消失、本工具 UI/音频进程退出；再次启动应成功且仍默认暂停。检查本地日志没有语音、PID、设备 ID 或原始异常详情。

## 已知局限

- 原保护策略本身不能区分恢复窗口内用户主动静音与意外静音；每周期最多尝试一次，不保证持续反复静音时仍有声音。
- 无法确认最初发出静音命令的进程，不保证全部设备、驱动和软件兼容。
- 暂停时录音状态显示为未监测；没有常驻录音监听。
- 本阶段不提供 EXE、隐藏终端启动器、开机自启、自动更新或正式发布。
- 无响应的系统调用只能通过结束专属子进程中止；正常 COM 清理可测试，强制结束路径由 Windows 回收该进程资源。
- 托盘真实播放恢复、设备插拔和多显示缩放效果待用户确认。不能把模拟测试或暂停烟雾测试描述为这些验收已经通过。
